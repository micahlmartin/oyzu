Historical checkpoints and outstanding lists below include defensive, repeatability and qualification work that must now be tracked separately from functional blockers. They must not automatically extend the implementation goal. Missing capabilities and failed required functional paths still need implementation and verification.

## Builder interfaces and module boundaries

Ecosystem-specific code is now owned by modules under `src/builders`, implementing a crate-private `Builder` trait. Discovery, toolchain selection, dependency preparation, typed planning and embedded runtime assets have explicit interface boundaries. The engine is split into lifecycle, planning, execution and bundle modules; it no longer selects native commands by package manager. Native report conversion remains in the shared report layer. See [builder code organization](builder-code-organization.md) for ownership and extension rules. This structural work preserves the existing supported behavior and does not expand the claimed builder acceptance scope.

Report evidence collection now has its own engine module, supporting OEP-0012's diagnostic bundle requirements. Contained reports up to 16 MiB are captured before parsing, so malformed native XML or invalid text remains inspectable with its digest while the action fails. Summaries are computed from the retained bytes. Focused tests cover invalid binary/text content, actual failed JUnit tests, unchanged captured evidence, and rejection of missing, oversized and escaping reports. This does not establish the full output-quota or filesystem race-resistance requirements.

Required builder reports now survive root and qualified TOML task overrides, addressing part of OEP-0005's override contract. The builder interface has an optional exact-command reporting adapter; Node owns recognition of simple `node --test` / `npm run test` bodies and their native reporter arguments. Unknown replacements retain their commands and receive concrete required test/coverage file destinations as environment variables. The engine does not apply native stdout parsing to arbitrary replacements. [Run 36843647009](https://github.com/micahlmartin/oyzu/actions/runs/36843647009) passed at `6c9de82ddc9bf2e9705aee6410e927cd75fbfbea`; downloaded bundles show three passing native tests and 10/10 covered lines for both the unchanged EX-009 override and a custom runner, and a failed bundle with no artifacts when a zero-exit replacement omitted both reports. EX-009 is not marked complete.

Task `reports` declarations now use typed registered formats with kind/path validation, rather than discarded JSON. Relative paths resolve against captured task cwd. Simple `*`, `?`, `**` globs collect sorted contained files with independent digests and summaries; empty or malformed matches fail the check. Declaring custom JUnit output retains the operation's coverage requirement.
