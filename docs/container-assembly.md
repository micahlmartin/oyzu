# Internal container assembly boundary

This is the executor boundary for Dockerfile-free application packaging in [OEP-0018](proposals/OEP-0018-container-and-helm-packaging/README.md). The first application integration is [Python container assembly](reference/python-containers.md), with its implemented profiles verified in Linux CI. It does not complete EX-012, general runtime profiles, startup smoke tests or the full container design.

## Ownership and contract

`executor/recipe` owns a finite data record: one base, declared copies, numeric UID/GID, an absolute image work directory and a literal argv entrypoint. It renders a deterministic Dockerfile containing only FROM, WORKDIR, COPY, USER, ENTRYPOINT and an empty CMD. Clearing CMD prevents an inherited base command from unexpectedly becoming arguments to the application's entrypoint. There are no script bodies, RUN, ARG, ENV, secret mounts, URL downloads, arbitrary instructions or expression evaluation in this record. Inherited base contents and runtime environment remain separate inputs.

Builders must choose compatible runtime profiles, entrypoints, runtime payloads and ownership. The executor cannot infer that a binary is static, that Python wheels match an interpreter, or that an application's dependencies are complete. Scratch is an explicit capability choice that a builder must justify with runtime facts. A captured base requires exactly one matching `ImageInput`; its canonical native name resolves through the existing immutable OCI context binding. An arbitrary registry string is insufficient. Native base admission, including unsupported ONBUILD rejection, remains required before constructing that binding.

`dependencies/images::capture` is the shared acquisition entry point for provisioned base images. Its typed request supplies the converter executor, private preparation destination, target platform and execution name; it accepts already admitted references and returns verified `ImageInput` bindings. It exports by immutable local image identity, converts through the isolated native OCI adapter, verifies platform/config agreement and captures each resulting store's tree identity. Existing Docker preparation uses this same owner. It neither pulls images nor resolves configuration nor establishes language-runtime compatibility. Application packaging must use this boundary rather than importing Docker builder internals or inventing another converter.

Copy sources are relative paths within the private selected context. Destinations and work directories are absolute image paths. Paths are bounded to 1,024 bytes and use portable literal ASCII components; traversal, aliases involving case-overlapping destinations, wildcard/variable expansion and instruction injection fail validation. A root work directory or destination is allowed. A recipe contains 1–256 copies and 1–64 entrypoint arguments, each at most 4,096 bytes without control characters. Rendered definitions are limited to 1 MiB. These are internal admission limits, not user configuration knobs. UID/GID and other runtime defaults belong to the builder profile; the renderer does not guess them.

## Plan and execution identity

Configuration resolution follows [the cascading configuration contract](reference/configuration.md). Builders register settings and consume the supplied target snapshot; they do not reread project/local files or environment overrides while constructing an image definition. The production Docker path obtains `docker.apparmorProfile` from resolved configuration during preparation and freezes it in the execution mode. The worker consumes that value without resolving it again. The legacy `OYZU_BUILDKIT_APPARMOR_PROFILE` variable is admitted only through the configuration engine's diagnosed compatibility input, including administrative constraints. Future application packaging must preserve this boundary; an image runtime profile is not a configuration profile or a grant of authority.

The existing private `Mode::Buildkit` has an optional `generated_recipe` field. Its `dockerfile_digest` must match SHA-256 of the rendered definition exactly. The full typed execution mode is already part of the frozen action record, so changing launch arguments, ownership, copies or base binding changes its planned identity. Unknown recipe fields are rejected. Ordinary Dockerfile modes omit the new field entirely, preserving their serialized shape.

`executor/worker` writes generated bytes only in its private definition directory, separate from the captured project and the selected COPY context. It never creates or rewrites a checkout Dockerfile. Normal source-owned Dockerfiles use the same staging boundary. The worker verifies the bytes actually staged for BuildKit against the planned digest, including a source change during copying; it refuses an existing definition destination. Materialization, input containment, context bounds, immutable base stores, network isolation, worker cleanup and OCI verification retain their existing owners.

Rendering does not acquire a base, compile an application, run its tests or certify an image's runtime behavior. `Builder::container_profile` supplies language-owned artifact/runtime requirements; `build/containers` composes shared acquisition, exact artifact materialization and isolated image actions. It creates a derived target with an empty source projection and the owning configuration digest. Python supplies the first profile. Matrix/profile expansion and application smoke-test actions remain required work.

## Verification

Local tests cover exact rendered bytes/digest, captured-base requirements, destination overlaps, path/instruction injection rejection, unsupported script fields, altered-plan rejection and private definition staging. Source-owned Dockerfile behavior remains covered by the existing build/worker checks.

An opt-in Rust conformance test calls the real isolated worker with a generated definition and no source Dockerfile. It requires two native OCI exports with identical image/archive identities, the copied payload's exact bytes and numeric ownership, expected image launch metadata and unchanged source. It does not execute an application or claim application smoke-test coverage. The test is compiled on every CLI host, skipped without provisioned infrastructure and explicitly run in the Linux worker job after provisioning. It passed at revision 06e0aed in [worker job 110876901667](https://github.com/micahlmartin/oyzu/actions/runs/37018406596/job/110876901667), alongside the existing compiled-CLI worker contract.

A second native check captures the provisioned `oyzu-fixture/alpine:amd64` base through the shared acquisition boundary, then assembles a payload over that exact binding twice. It verifies the native base runtime and copied payload are retained, image launch metadata and numeric ownership are correct, identities repeat and captured source/base stores remain unchanged. CI retains its evidence under `worker-recipe-evidence/captured-base`. This passed at revision 187009c in [worker job 110880663213](https://github.com/micahlmartin/oyzu/actions/runs/37019458164/job/110880663213). It proves acquisition-to-assembly composition, not application execution.

With a provisioned Linux worker and AppArmor profile, the check is:

```text
cargo test --locked --lib executor::worker::native_recipe::generated_recipe_builds_reproducible_native_oci_without_a_source_dockerfile -- --ignored --exact
cargo test --locked --lib dependencies::images::native::captured_base_feeds_generated_assembly_without_source_dockerfile -- --ignored --exact
```

Set `OYZU_TEST_RECIPE_APPARMOR_PROFILE` to the explicitly provisioned AppArmor profile before running this test (`oyzu-buildkit` in CI). This required test-harness input constructs a frozen executor fixture; it is not a public configuration override and does not exercise policy resolution. CI sets `OYZU_RECIPE_EVIDENCE_DIR=worker-recipe-evidence` to retain execution-mode data, worker logs and native OCI archives alongside the existing worker evidence. No local Docker engine is started by ordinary tests. Dockerfile instruction semantics follow the [native Dockerfile reference](https://docs.docker.com/reference/dockerfile/).


## Prepared dependency-context transport

`Mode::Buildkit` now accepts an optional internal `dependency_context` record with a contained store path under `contexts/`, a captured tree digest and a target platform. The worker copies that exact prepared subtree into private staging and exposes only that copy through the named local context `dependencies`. It uses the existing prepared-tree capture rules and limits (100,000 entries and 10 GiB), including portable paths and link/reparse-point rejection. Changed bytes, a mismatched target platform, missing read-only preparation mount or a conflicting captured image named `dependencies` fail before worker startup. Root `.dockerignore` files are rejected so BuildKit cannot silently filter an already captured store. Original prepared inputs are never mounted into the worker.

The argument binding uses BuildKit's [named local context implementation](https://github.com/moby/buildkit/blob/v0.25.0/frontend/dockerui/namedcontext.go): `--local dependencies=/inputs/dependencies` and `--opt context:dependencies=local:dependencies`. Native Dockerfiles can consume it with `RUN --mount=type=bind,from=dependencies,target=/packages` or `COPY --from=dependencies`. The worker retains no-network execution, private stores, no result-cache import and immutable base-image inputs. The transport does not authorize arbitrary context URLs or secret mounts. An omitted field preserves the previous serialized mode and behavior.

This internal transport is now consumed by experimental [Python dependency profiles](reference/docker-images.md#offline-pip-dependency-context-experimental) for pip, uv and Poetry and the [npm tarball profile](reference/docker-images.md#offline-npm-dependency-context-experimental). Native Docker metadata identifies the reserved external context and original consuming base; shared acquisition composition selects a registered provider and applies resolved owner policy before network preparation. Python prepares its wheel store and hashed install manifest; npm reuses its verified locked registry tarballs. Preparation uses the exact immutable base, and only the provider's store subtree is captured. This does not complete EX-058 or support all managers. A digest establishes content integrity, not absence of secrets or approved provenance; private connector and package provenance integration remain unfinished.

Pure tests exercise private subtree identity, sibling exclusion, tampering, wrong platforms, ignore-file rejection, path admission, argument binding, base-context collision and absent-field compatibility. An opt-in native worker test consumes the same prepared file through both a read-only RUN mount and COPY, rejects a write attempt, checks exact resulting layer bytes and exclusion of an unrelated sibling canary, then requires identical image/archive identities on a second export. It also verifies source/prepared stores remain unchanged. This passed at revision 3a28853 in [Linux worker job 110901294087](https://github.com/micahlmartin/oyzu/actions/runs/37025526684/job/110901294087). CI retains the mode, logs and OCI archives under `worker-recipe-evidence/dependency-context`. The conformance fixture contains ordinary package-like bytes, not a resolved Python/npm/native package closure, and therefore does not establish package-manager installation support.
