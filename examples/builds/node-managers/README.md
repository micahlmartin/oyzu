# EX-019: Equivalent npm pnpm and Yarn projects

Status: **design contract for review**. Intended hosts: Windows, macOS, Linux. See the [validation scope](../../VERIFICATION.md).

## Purpose

- Select the package manager matching the native lock and packageManager metadata.
- Competing locks are an explicit negative case, not normal fixture state.

## Review the project

Open the checked-in project roots: `npm`, `pnpm`, `yarn`. Source, native manifests, and Oyzu configuration are included here so we can review the intended experience directly.

The intended Oyzu interface is:

```text
oyzu build
```


No build YAML is required for this scenario. Configuration, where present, demonstrates only the feature under discussion.

## Native checks available now

With the named toolchains already installed, run:

```text
# From npm
node --test

# From pnpm
node --test

# From yarn
node --test
```

Native commands document the underlying ecosystem workflow. They are supporting context, not a prerequisite for accepting or revising this design contract.

## Failure and variation cases

- **competing-locks:** Copy another variant's lock into one project. Expected: Explain conflicting manager evidence.
- **yarn-selective-resolutions:** Build `variants/yarn-resolutions` with native Yarn Classic. Its `package.json` retains direct `is-number` 6.0.0 while overriding `is-odd/is-number` to 7.0.0. The checked-in lock was generated by Yarn 1.22.22; five native tests include assertions against both installed versions. Oyzu should collect JUnit/coverage and a snapshot package without an Oyzu configuration file. A changed override with a stale lock must fail before project hooks run, even when both versions are captured. Native host verification and Linux build acceptance have separate scopes; see the [Yarn reference](../../../docs/reference/yarn.md).
